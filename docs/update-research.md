# 分布式自动更新方案调研（P2P 房间内互为更新源）

> 问题：能否让每个客户端设置"从其他分布式终端主动更新到最新版"？
> 现状：全平台**零自动更新**——每次升级都要手动去 GitHub 下载安装（FengGpd/xfold6
> 的版本滞后就是这么来的）；GitHub 直连在国内间歇性阻断。

## 一、结论：可行，且本项目 unusually 契合

分布式更新 = "把安装包当作一个文件，在房间里 P2P 分发"。这正好落在已建成的
filex 基础设施上：

| 更新需要的能力 | filex 现状 |
|---|---|
| 大文件分块传输（包体 ~140MB） | ✅ 分块/滑动窗口/FEC/流压缩/pacing |
| 内容完整性 | ✅ fid=SHA-256 内容寻址 + 块哈希清单 + finalize 终检 |
| 断点续传（弱网/重启） | ✅ 接收方位图持久化 |
| 多人同时更新（swarm） | ✅ 多源种子协议 fx-want/fx-hold/fx-req（多持有者并发拉块） |
| 传输通道 E2EE | ✅ 全部走既有双传输 |
| 版本发现 | ✅ presence/ctl 帧可捎带（hubInfo 同款模式） |
| 版本偏差容忍 | ✅ 协议层混版兼容（握手兼容/渲染自愈），更新非紧急操作 |

**独有优势**：一旦某成员更新成功，其 files/ 目录天然持有完整包（v1.21.2 发送方
落盘）→ 自动成为种子 → 全房间 swarm 式传播，越多人更新越快。

## 二、架构设计

```
版本发现        presence 心跳捎带 ver + 最新已知包清单（gossip，版本号高者胜）
   │
种子来源        任一客户端从 GitHub Release 下载（或上一轮 P2P 更新成功后自动持有）
   │
分发            过期成员按策略 fx-want → 多源并发拉块（filex 既有路径，零新传输代码）
   │
校验            Ed25519 签名的发布清单（开发者私钥签，公钥烧进客户端）
                + SHA-256 终检 + 版本单调（禁降级）——P2P 源不可信的三道闸
   │
暂存            userData/staging/（不动运行中的 app）
   │
应用            用户确认 → 退出时原子换装（平台各异，见 §3）→ 重启即新版 → 自动成为种子
```

### 各平台"换装"机制
- **Linux AppImage**：单文件原子替换（下载→chmod→重启时 swap），最简单；
- **macOS zip**：staging 解压 → 退出时 ditto 覆盖 /Applications/OrayChat.app → 重启
  （filex 直写的文件**不带 quarantine xattr**——比浏览器下载少一道 Gatekeeper 坑）；
- **Windows NSIS**：staging 保存 → 退出时静默安装（/S）→ 重启；
- **Android APK**：filex 下载 → 系统安装器**一键确认**（WebView 无法静默装，
  "辅助更新"而非全自动——这是 Android 平台的安全边界，不可绕）；
- **iOS**：不做（无 TestFlight/AppStore 通道）。

### 设置项（用户要求"可以设置"）
- 更新策略：关闭 / 提示我 / 自动下载后提示安装 / 退出即装（四档）；
- 更新源：仅同伴（纯分布式）/ 同伴优先 + GitHub 兜底 / 仅 GitHub；
- 每个"不更新此版本"的记忆（kv 存已忽略版本）。

## 三、风险与对策

| 风险 | 对策 |
|---|---|
| **P2P 源被投毒**（恶意成员发篡改包） | Ed25519 签名清单（私钥在 CI secret，公钥硬编码）+ SHA-256 终检 + 版本单调；**无有效签名一律拒绝**——这是整个方案的安全底线 |
| 自换装竞态（更新时正在传文件/聊天） | 传输保护：filex 活跃时挂起换装；换装仅在用户确认/退出时执行 |
| 磁盘占用（staging ~300MB） | 安装完成即清 staging；种子文件保留（它就是 files/ 的正常文件） |
| 首次引导（鸡生蛋） | 房间内无任何新版本持有者时回落 GitHub 直下（带重试/镜像前缀，既有经验） |
| 冷启动房间全旧版 | 同上；且可在设置页手动"从 Release 拉取最新包成为种子" |
| 主进程 vs 渲染层分工 | 传输走渲染层 filex（现成）；**换装必须在主进程**（FS 权限 + 退出时机）——新增 updater IPC |

## 四、实施路线（拍板后）

- **P0（~2-3 天）**：桌面端分布式更新主链路——版本 gossip（presence 捎带 ver/pkg）
  + CI Ed25519 签名清单 + 更新策略设置页 + filex 多源拉包 + 校验/暂存 +
  退出换装（macOS 先行）+ 更新成功自动成为种子
- **P1（+1-2 天）**：Windows NSIS 静默换装 + Linux AppImage 原子换装 + GitHub
  兜底直下 + "重启并更新"UX
- **P2（+1 天）**：Android 辅助更新（APK 经 filex 到机 → 系统安装器一键装）
- **不做**：iOS；强推更新（版本偏差协议层已兼容，更新永远可拒绝）

## 五、需要拍板的点

1. 签名私钥管理：CI secret 存 Ed25519 私钥（每 tag 自动签清单）——与现有
   keystore.properties 同模式；
2. 默认策略建议：同伴优先 + GitHub 兜底，"自动下载后提示安装"（不用全自动）；
3. 是否把"中继主机"默认设为自动拉新包的种子源（推荐：是，骨干成员常开）。
