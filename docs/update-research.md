# 分布式自动更新方案调研（P2P 房间内互为更新源）

> 问题：能否让每个客户端设置"从其他分布式终端主动更新到最新版"？
> 现状：全平台**零自动更新**——每次升级都要手动去 GitHub 下载安装（FengGpd/xfold6
> 的版本滞后就是这么来的）；GitHub 直连在国内间歇性阻断。

## 一、结论：可行，且本项目 unusually 契合

分布式更新 = "把安装包当作一个文件，在房间里 P2P 分发"。这正好落在已建成的
filex 基础设施上：

| 更新需要的能力 | filex 现状 |
|---|---|
| 大文件分块传输（包体 ~140MB） | ✅ 分块/滑动窗口/FEC/流压缩/pacing |
| 内容完整性 | ✅ fid=SHA-256 内容寻址 + 块哈希清单 + finalize 终检 |
| 断点续传（弱网/重启） | ✅ 接收方位图持久化 |
| 多人同时更新（swarm） | ✅ 多源种子协议 fx-want/fx-hold/fx-req（多持有者并发拉块） |
| 传输通道 E2EE | ✅ 全部走既有双传输 |
| 版本发现 | ✅ presence/ctl 帧可捎带（hubInfo 同款模式） |
| 版本偏差容忍 | ✅ 协议层混版兼容（握手兼容/渲染自愈），更新非紧急操作 |

**独有优势**：一旦某成员更新成功，其 files/ 目录天然持有完整包（v1.21.2 发送方
落盘）→ 自动成为种子 → 全房间 swarm 式传播，越多人更新越快。

## 二、架构设计

```
版本发现        presence 心跳捎带 ver + 最新已知包清单（gossip，版本号高者胜）
   │
种子来源        任一客户端从 GitHub Release 下载（或上一轮 P2P 更新成功后自动持有）
   │
分发            过期成员按策略 fx-want → 多源并发拉块（filex 既有路径，零新传输代码）
   │
校验            Ed25519 签名的发布清单（开发者私钥签，公钥烧进客户端）
                + SHA-256 终检 + 版本单调（禁降级）——P2P 源不可信的三道闸
   │
暂存            userData/staging/（不动运行中的 app）
   │
应用            用户确认 → 退出时原子换装（平台各异，见 §3）→ 重启即新版 → 自动成为种子
```

### 各平台"换装"机制
- **Linux AppImage**：单文件原子替换（下载→chmod→重启时 swap），最简单；
- **macOS zip**：staging 解压 → 退出时 ditto 覆盖 /Applications/OrayChat.app → 重启
  （filex 直写的文件**不带 quarantine xattr**——比浏览器下载少一道 Gatekeeper 坑）；
- **Windows NSIS**：staging 保存 → 退出时静默安装（/S）→ 重启；
- **Android APK**：filex 下载 → 系统安装器**一键确认**（WebView 无法静默装，
  "辅助更新"而非全自动——这是 Android 平台的安全边界，不可绕）；
- **iOS**：不做（无 TestFlight/AppStore 通道）。

### 设置项（用户要求"可以设置"）
- 更新策略五档：关闭 / 提示我 / 下载后提示安装 / 退出即装 / **全自动（下载+换装+自动重启）**；
- 更新源：仅同伴（纯分布式）/ 同伴优先 + GitHub 兜底 / 仅 GitHub；
- 每个"不更新此版本"的记忆（kv 存已忽略版本，仅对"提示我"档生效）。

### 「全自动」档的平台边界与守门条件（用户问询确认）
- **桌面三平台可行**：下载→验签→暂存后，应用自行退出→换装→自动重启
  （macOS/Windows 用脱离的 helper 进程等退出后换装再拉起；Linux AppImage
  单文件原子 swap 最简）。重启 ~2-3s，聊天记录是本地持久化的，重启后自动
  重握手/续传，无数据丢失。
- **守门条件（全自动必须全部满足才动手）**：
  1. filex 无活跃传输（传输保护不变量）；
  2. 验签 + SHA-256 + 版本单调三闸全过；
  3. 崩溃环保护：距上次"自动更新重启">10 分钟（防坏包重启循环；连续 2 次失败
     自动降级为"提示安装"并告警）；
  4. 换装失败回退：staging 保留旧版备份，启动自检失败可回滚（P1 实现）。
- **Android 例外**：系统安全边界，APK 安装必须用户点击确认——全自动在该平台
  自动降级为"下载完成 → 一键安装提示"（半自动）。
- 建议：默认档仍是"下载后提示安装"；全自动按客户端逐台开启（常开的桌面机/
  中继主机适合全自动，手机用半自动）——正符合"各个客户端各自设置"。

### ⚠️ 与后台服务的冲突分析（全自动 vs 中继主机/托盘驻留）——必须专门设计

**冲突是真实的，且正打在骨干上**：

1. **中继主机自更新 = 全房间私有链闪断**。主机重启窗口内（app 退出→换装→重启
   →cloudflared 重注册边缘 ≈ 15-30s），所有成员的稳定地址断连。缓解底线：并联
   链路自动回落公共 broker（E2EE 不变，房间照常运转——私有中继研究的设计原则
   "私有链宕机自动回落公共双链=不新增故障模式"），但稳定地址确实闪一下。
2. **全员同时自动重启**：版本 gossip 传播很快，若多台客户端都开全自动，可能
   近乎同时退出换装——多台中继主机的房间可能瞬间零主机。
3. **换装 helper 与托盘驻留**：退出必须走 isQuiting 路径（绕过关窗即隐藏）；
   重启后恢复"重启前是隐藏在托盘还是前台可见"的状态。

**守门条件补两条（全自动档）**：

5. **错峰抖动**：每个客户端对"何时应用"加 0-30min 随机抖动——把同时重启的
   概率摊平；多主机房间天然错开。
6. **主机感知推迟（关键）**：本机是中继主机且 hub.memberList 非空（正在服务
   成员）→ 推迟应用，直到：服务空闲（成员清空 ≥10min）或到达维护窗口
   （可配置，默认凌晨 04:00，硬期限 72h——总得更新，不能永挂）。非主机成员
   无此约束。多主机房间配合错峰抖动，任一时刻至少一台主机在线。
7. **cloudflared 二进制随包更新**：换装后启动时按版本号刷新 userData 里的
   cloudflared 副本（现复制逻辑补"版本不同才复制"），隧道用新二进制重启。

（"退出即装"档同样受 5/6 约束——手动更新今天也会断中继，只是人在旁边挑时机；
自动化的意义就是把这份判断交给规则。）

## 三、风险与对策

| 风险 | 对策 |
|---|---|
| **P2P 源被投毒**（恶意成员发篡改包） | Ed25519 签名清单（私钥在 CI secret，公钥硬编码）+ SHA-256 终检 + 版本单调；**无有效签名一律拒绝**——这是整个方案的安全底线 |
| 自换装竞态（更新时正在传文件/聊天） | 传输保护：filex 活跃时挂起换装；换装仅在用户确认/退出时执行 |
| 磁盘占用（staging ~300MB） | 安装完成即清 staging；种子文件保留（它就是 files/ 的正常文件） |
| 首次引导（鸡生蛋） | 房间内无任何新版本持有者时回落 GitHub 直下（带重试/镜像前缀，既有经验） |
| 冷启动房间全旧版 | 同上；且可在设置页手动"从 Release 拉取最新包成为种子" |
| 主进程 vs 渲染层分工 | 传输走渲染层 filex（现成）；**换装必须在主进程**（FS 权限 + 退出时机）——新增 updater IPC |

## 四、实施路线（拍板后）

- **P0（~2-3 天）**：桌面端分布式更新主链路——版本 gossip（presence 捎带 ver/pkg）
  + CI Ed25519 签名清单 + 更新策略设置页 + filex 多源拉包 + 校验/暂存 +
  退出换装（macOS 先行）+ 更新成功自动成为种子
- **P1（+1-2 天）**：Windows NSIS 静默换装 + Linux AppImage 原子换装 + GitHub
  兜底直下 + "重启并更新"UX
- **P2（+1 天）**：Android 辅助更新（APK 经 filex 到机 → 系统安装器一键装）
- **不做**：iOS；强推更新（版本偏差协议层已兼容，更新永远可拒绝）

## 四点五、发布的发布侧流程（tag → 清单 → swarm）

现有发版流程**完全不变**（用户指令 → bump/tag/推 CI → 五平台构建 9 资产 → Release
清理只留最新），分布式层只新增**一个 CI 步骤**：

1. **CI 签名清单**（新增的收尾 job，各平台构建完成后运行）：
   - 拉取本次 Release 全部资产 → 逐个算 SHA-256；
   - 生成清单 `manifest.json`：`{ v: "1.29.0", ts, assets: { "mac-zip": {size,
     sha256, fid}, "win-nsis": {...}, "linux-appimage": {...}, "android-apk": {...} } }`
     （fid = sha256 前 24hex，与 filex 内容寻址天然对齐）；
   - 用 Ed25519 私钥（CI secret）签名 → `manifest.json` 与 `manifest.sig` 作为
     两个额外资产上传 Release（9 → 11 资产）。
   - **清单本身就是"发布物"进入 P2P 网**：它只有 1-2KB，随 presence/ctl 心跳
     直接 gossip 全房间（E2EE 通道）——版本发现的延迟 = 一个心跳周期，与包体
     大小无关。

2. **种子获取**（客户端侧行为，三选一自动+手动）：
   - 中继主机（或任何开了"自动获取"策略的成员）看到清单 → GitHub 直下本平台
     资产 → 校验签名/SHA → 落 files/ 成为种子；
   - 或任一成员设置页点「从 Release 拉取最新包成为种子」；
   - 或上一轮更新成功的客户端天然持有（swarm 自增殖）。

3. **成员侧**（呼应 §二）：心跳 gossip 的清单带签名 → 本机版本号落后且策略允许
   → fx-want 拉包（多源）→ 校验 → 暂存 → 确认后换装。

4. **版本治理**：
   - 单调性：客户端只接受比自身新的版本（禁降级）——回滚 = 发布一个更高的
     hotfix 版本，而不是撤回；
   - 误发版处置：直接删 Release 资产可以阻断新种子获取（已分发的包靠版本单调
     +下一版修复）；
   - 密钥轮换：清单允许同时携带新旧两把公钥的签名（过渡期双签）。

5. **发布节奏**：维持既定纪律——只在用户明确指令时发版；分布式自动更新改变的
   是"分发"，不是"何时发"。

## 五、需要拍板的点

1. 签名私钥管理：CI secret 存 Ed25519 私钥（每 tag 自动签清单）——与现有
   keystore.properties 同模式；
2. 默认策略建议：同伴优先 + GitHub 兜底，"自动下载后提示安装"（不用全自动）；
3. 是否把"中继主机"默认设为自动拉新包的种子源（推荐：是，骨干成员常开）。
